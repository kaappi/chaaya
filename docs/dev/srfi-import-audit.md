## Note on built-in vs. portable SRFI shadowing

Several SRFI numbers (e.g. 1, 13, 69) have **both** a native built-in
implementation registered in `ch_vm_register_primitives` /
`library_builtin.c` **and** a portable `.sld` under `lib/srfi/`. This is
intentional: `ch_ensure_library` (`src/library.c`) looks up
`vm->libraries` (built-ins) first and only falls back to resolving and
loading a `.sld` from `--lib-path` when no built-in registration exists.
The portable shadow files exist for documentation/reference and for
hosts that don't register the built-in, but built-ins always win when
both are present. Do not delete the portable shadows.

## Remaining failure categories

The rest of the failures below fall into a few buckets that are each
bigger than a "missing primitive" fix:

1. **Native sub-library never ported from Kaappi (Zig) to Chaaya (C)** --
   `library not found: srfi.NNN.primitives` (131, 136, 137, 150, 181,
   237, 240, 57) and `srfi.160.primitives` (4, 63, 66, 74, 231). These
   `.sld` files were carried over from Kaappi's tree and depend on
   substantial native features Chaaya doesn't have yet: a record-type-
   descriptor engine (237/57/131/136/150), a `NumericVector` heap type
   (160, and 4/63/66/74 which sit on top of it), custom ports (181),
   and syntax-parameter/explicit-renaming macros (211). Each is a
   standalone feature project, not a primitive-list gap.
2. **Kaappi-only helper libraries** -- `library not found: kaappi.sysinfo`
   (59, 112, 193) and `kaappi.primitives` (271): these `.sld` files
   assume Kaappi-specific runtime introspection that has no Chaaya
   equivalent.
3. **Exporting a special form as a library binding** -- `define-library:
   exported binding 'X' is undefined` for `cond-expand` (0),
   `let-values`/`let*-values` (11, 234), `case-lambda` (16), `guard`
   (34), `delay` (45), `either` (189, a normal export that fails
   because the library also exports `values->maybe`'s sibling forms --
   see the file for the actual name collision), `define-property` (213,
   an engine-level compiler form), and `_` (257, a pattern-matcher
   literal). Compiler special forms and syntax-only bindings aren't
   ordinary global values, so a portable library can't easily
   re-export them; needs expander/library support for syntax exports,
   not a VM primitive.
4. **Importing a special form as a value** -- `import only/except:
   identifier 'X' not found in import set` for `define-syntax`/
   `syntax-rules` (139, 147, 148, 149, 46), `define-values` (244),
   `guard` (248), and `let` (71): same root cause as #3, from the
   importing side.
5. **Needs deeper triage** -- `wrong number of arguments` at library
   load time (44, 113, 146, 162, 167, 168, 228) and a bare runtime
   `error` during load (36); likely a `define-record-type` /
   `define-condition-type` arity mismatch worth its own investigation.
